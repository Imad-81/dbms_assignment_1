Review 2 · Normalized Database Design

Normalization Journey: 1NF → 2NF → 3NF

Every table in the HAPCMS schema satisfies Third Normal Form. Below is the normalization rationale applied to representative violations found and fixed.

1NF
First Normal Form — Atomic Values & No Repeating Groups
Violation found: A flat “patient_record” table stored multiple phone numbers as comma-separated strings and prescription data as repeating columns (med1, med2, med3…).
Fix: Phone extracted to patient_contact; prescription items moved to prescription_item(item_id, prescription_id, drug_name, dosage, qty). All columns are now atomic.
2NF
Second Normal Form — No Partial Dependencies on Composite Keys
Violation found: A flat booking table with composite PK (appointment_id, patient_id) stored patient_name — depending only on patient_id, not the full key.
Fix: Patient attributes moved exclusively to patient table. appointment references patient_id as FK. Every non-key attribute now depends on the whole PK.
3NF
Third Normal Form — No Transitive Dependencies
Violation found: A merged appointment table stored doctor_id → department_name → department_head. Department info transitively depended on doctor_id via department_id.
Fix: department(dept_id, dept_name, dept_head, location) extracted as standalone entity. Doctors reference department_id as FK. Zero transitive dependency chains remain.
Conclusion: All 16 tables verified to satisfy 3NF. Decomposition is lossless and dependency-preserving. No BCNF violations detected.

Walk through each form: 1NF — repeating groups are the most obvious violation in hospital systems. 2NF — only matters with composite keys, which applies to junction tables. 3NF — the trickiest: department head data inside doctor records is a classic transitive dependency.

Emphasize: We are not just claiming 3NF; we can demonstrate it attribute-by-attribute using functional dependencies on the next slide.

Key emphasis: Functional dependencies are the mathematical proof of normalization. The left side is always the primary key; the right side are non-key attributes. Point out how department info is never on the right side of the doctor table's FD — it lives only in the department table.

If challenged: BCNF is verified — every determinant is a superkey. There are no hidden candidate keys that would cause a 3NF-but-not-BCNF situation.

Review 2 · DDL Implementation

DDL Scripts — Patient, Doctor & Appointment Tables

Production-ready CREATE TABLE statements with all applicable constraints enforcing business rules at the database engine level.

-- Patient Table CREATE TABLE patient ( patient_id SERIAL PRIMARY KEY, first_name VARCHAR(60) NOT NULL, last_name VARCHAR(60) NOT NULL, dob DATE NOT NULL, gender CHAR(1) CHECK (gender IN ('M','F','O')), blood_group VARCHAR(4) CHECK (blood_group IN ( 'A+','A-','B+','B-', 'AB+','AB-','O+','O-')), phone VARCHAR(15) UNIQUE NOT NULL, email VARCHAR(120) UNIQUE, registered_on DATE DEFAULT CURRENT_DATE );
-- Doctor Table CREATE TABLE doctor ( doctor_id SERIAL PRIMARY KEY, first_name VARCHAR(60) NOT NULL, last_name VARCHAR(60) NOT NULL, specialization VARCHAR(80) NOT NULL, license_no VARCHAR(30) UNIQUE NOT NULL, department_id INT REFERENCES department(department_id), phone VARCHAR(15) NOT NULL );
-- Appointment (enforces no double-booking) CREATE TABLE appointment ( appointment_id SERIAL PRIMARY KEY, patient_id INT NOT NULL REFERENCES patient(patient_id), doctor_id INT NOT NULL REFERENCES doctor(doctor_id), appt_date DATE NOT NULL CHECK (appt_date >= CURRENT_DATE), appt_time TIME NOT NULL, status VARCHAR(15) DEFAULT 'Scheduled' CHECK (status IN ( 'Scheduled','Completed', 'Cancelled','No-show')), reason TEXT, -- Core Business Rule: No overlapping doctor slots CONSTRAINT uq_doctor_slot UNIQUE (doctor_id, appt_date, appt_time) ); -- Admission Table CREATE TABLE admission ( admission_id SERIAL PRIMARY KEY, patient_id INT NOT NULL REFERENCES patient(patient_id), doctor_id INT REFERENCES doctor(doctor_id), bed_id INT NOT NULL REFERENCES bed(bed_id), admit_date DATE NOT NULL DEFAULT CURRENT_DATE, discharge_date DATE CHECK (discharge_date >= admit_date), status VARCHAR(15) DEFAULT 'Active' CHECK (status IN ('Active','Discharged')) );

Left column: Patient table — every constraint maps to a business rule. Blood group CHECK with explicit enum, phone UNIQUE to prevent duplicate registrations.

Right column: The UNIQUE constraint on (doctor_id, appt_date, appt_time) is the most important constraint in the system. discharge_date CHECK prevents impossible date sequences. Status CHECK enumerates valid state machine transitions.

Integrity Enforcement

All Five Business Rules — Database Enforcement Strategy

Each business rule from the project specification is enforced at the database engine level, not just the application layer.

UNIQUE
No Overlapping Doctor Appointments — CONSTRAINT uq_doctor_slot UNIQUE (doctor_id, appt_date, appt_time) on appointment. The database engine rejects any INSERT or UPDATE that would place two patients with the same doctor at the same date and time. No application-side lock required.
CHECK + TRIGGER
One Active Patient Per Bed — A BEFORE INSERT/UPDATE trigger on admission queries: SELECT COUNT(*) FROM admission WHERE bed_id = NEW.bed_id AND status = 'Active'. If count > 0, trigger raises an exception. bed.is_occupied is updated automatically.
CHECK
Valid Admission / Discharge Dates — CHECK (discharge_date IS NULL OR discharge_date >= admit_date) on admission. Discharge is initially NULL (patient admitted) and only set on formal discharge clearance.
CHECK
Positive Charges — CHECK (unit_charge > 0) on bill_item and CHECK (amount > 0) on bill. Prevents zero or negative billing entries which would indicate data corruption or unrecorded credit notes.
CHECK + TRIGGER
Payment Cannot Exceed Bill Total — CHECK (amount_paid <= total_amount) on payment, combined with a trigger that recalculates bill.paid_amount after each payment insert. bill.status automatically transitions to 'Paid' when paid_amount = total_amount.

Review 2 · SQL Queries

SQL Queries — Joins, Subqueries & Aggregation

Meaningful queries spanning multiple tables, demonstrating INNER JOIN, LEFT JOIN, correlated subqueries, and aggregate functions with GROUP BY.

-- Patient Appointment History with Doctor & Department details SELECT p.first_name || ' ' || p.last_name AS patient_name, d.first_name || ' ' || d.last_name AS doctor_name, dept.dept_name, a.appt_date, a.appt_time, a.status, c.chief_complaint, diag.icd_code, diag.description FROM appointment a INNER JOIN patient p ON a.patient_id = p.patient_id INNER JOIN doctor d ON a.doctor_id = d.doctor_id INNER JOIN department dept ON d.department_id = dept.department_id LEFT JOIN consultation c ON c.appointment_id = a.appointment_id LEFT JOIN diagnosis diag ON diag.consultation_id = c.consultation_id WHERE p.patient_id = 1 ORDER BY a.appt_date DESC;
-- Doctor Weekly Schedule: all booked slots with patient name SELECT d.first_name || ' ' || d.last_name AS doctor_name, dept.dept_name, a.appt_date, a.appt_time, a.status, p.first_name || ' ' || p.last_name AS patient_name, p.phone FROM doctor d INNER JOIN department dept ON d.department_id = dept.department_id INNER JOIN appointment a ON a.doctor_id = d.doctor_id LEFT JOIN patient p ON a.patient_id = p.patient_id WHERE d.doctor_id = 2 AND a.appt_date BETWEEN '2026-09-20' AND '2026-09-27' ORDER BY a.appt_date, a.appt_time;
-- Patients with outstanding bills (subquery) SELECT p.patient_id, p.first_name || ' ' || p.last_name AS patient_name, p.phone FROM patient p WHERE p.patient_id IN ( SELECT DISTINCT patient_id FROM bill WHERE status IN ('Unpaid', 'Partially Paid') ); -- Pending diagnostic tests SELECT p.first_name || ' ' || p.last_name AS patient_name, t.test_name, tor.ordered_on, tor.status FROM test_order tor INNER JOIN test t ON tor.test_id = t.test_id INNER JOIN patient p ON tor.patient_id = p.patient_id WHERE tor.status = 'Pending' ORDER BY tor.ordered_on;
-- Revenue by Department (aggregation) SELECT dept.dept_name, COUNT(DISTINCT a.appointment_id) AS total_appts, SUM(b.total_amount) AS gross_revenue, SUM(b.paid_amount) AS collected, SUM(b.total_amount - b.paid_amount) AS outstanding FROM department dept INNER JOIN doctor d ON d.department_id = dept.department_id INNER JOIN appointment a ON a.doctor_id = d.doctor_id INNER JOIN bill b ON b.patient_id = a.patient_id GROUP BY dept.dept_name ORDER BY gross_revenue DESC;

Tab 1 — INNER JOIN: Patient history across 6 tables. LEFT JOINs to consultation and diagnosis handle upcoming appointments that have no consultation yet.

Tab 2 — LEFT JOIN: Doctor's weekly schedule with all booked slots.

Tab 3 — Subquery: Outstanding bills using IN subquery; pending tests using a 3-table join. Both are critical daily operational queries.

Tab 4 — Aggregation: Revenue report by department using COUNT DISTINCT, SUM and GROUP BY. This is the management-level query that justifies the entire database investment.

Review 2 · Views & Reports

Six Database Views for Operational Reporting

Pre-defined views encapsulate complex joins for repeatable, role-specific access to critical hospital data without exposing raw table structure.

VIEWvw_patient_history
Full longitudinal record per patient: appointments, consultations, diagnoses, prescriptions, test results and admissions ordered by date. Used by doctors at point-of-care.
CREATE VIEW vw_patient_history AS SELECT p.patient_id, p.first_name||' '||p.last_name AS patient, a.appt_date, d.last_name AS doctor, c.chief_complaint, diag.icd_code, diag.description FROM patient p LEFT JOIN appointment a ON a.patient_id = p.patient_id LEFT JOIN doctor d ON d.doctor_id = a.doctor_id LEFT JOIN consultation c ON c.appointment_id = a.appointment_id LEFT JOIN diagnosis diag ON diag.consultation_id = c.consultation_id ORDER BY a.appt_date DESC;
VIEWvw_doctor_schedule
Today's and upcoming slots per doctor with patient name, time and status. Used by reception and doctors to manage their daily queue.
VIEWvw_pending_tests
All test orders where status = 'Pending'. Displays patient name, test name, ordering doctor and date ordered. Consumed daily by the laboratory.
VIEWvw_bed_occupancy
Real-time ward and bed occupancy: ward name, bed number, type, is_occupied, current patient and admit date. Used by ward supervisors.
CREATE VIEW vw_bed_occupancy AS SELECT w.ward_name, b.bed_number, b.bed_type, b.is_occupied, p.first_name||' '||p.last_name AS current_patient, adm.admit_date FROM bed b INNER JOIN ward w ON b.ward_id = w.ward_id LEFT JOIN admission adm ON adm.bed_id = b.bed_id AND adm.status = 'Active' LEFT JOIN patient p ON p.patient_id = adm.patient_id ORDER BY w.ward_name, b.bed_number;
VIEWvw_outstanding_bills
All bills with status 'Unpaid' or 'Partially Paid': patient name, total, amount paid, and outstanding balance. Used by billing department for collection follow-up.
VIEWvw_revenue_by_dept
Gross revenue, collected and outstanding receivables grouped by department. Aggregates across all bills linked through appointments. Management-level reporting view.

Key point: Views serve two purposes — (1) simplifying complex multi-table queries for the application layer, and (2) providing an abstraction layer so schema changes don't break application code. All 6 views from the specification are implemented and return meaningful results from sample data.

Performance Optimization

Indexing Strategy — Frequently Searched Attributes

Indexes created on columns appearing in WHERE clauses, JOIN conditions, and ORDER BY of operational views and frequent queries.

-- Appointment lookup by doctor + date (schedule view) CREATE INDEX idx_appt_doctor_date ON appointment(doctor_id, appt_date); -- Appointment lookup by patient (history view) CREATE INDEX idx_appt_patient ON appointment(patient_id); -- Admission active bed lookup (occupancy trigger) CREATE INDEX idx_admission_bed_status ON admission(bed_id, status); -- Outstanding bill filter CREATE INDEX idx_bill_status ON bill(patient_id, status); -- Pending test orders CREATE INDEX idx_test_order_status ON test_order(status, ordered_on); -- Patient phone & email lookups (login / search) CREATE INDEX idx_patient_phone ON patient(phone); CREATE INDEX idx_patient_email ON patient(email);
Index Design Principles Applied
  • Composite indexes on (doctor_id, appt_date) align with the schedule view's WHERE clause — avoids full table scan.
  • UNIQUE constraints on (doctor_id, appt_date, appt_time) implicitly create a B-tree index — no duplicate index needed.
  • Phone & email indexed because patient search at reception is the most frequent real-time query in the system.
  • Composite bill index on (patient_id, status) supports the outstanding bills view filter efficiently.
EXPLAIN ANALYZE Result (Sample)
Query: doctor schedule for doctor_id = 2
Before index: Seq Scan — 18 ms
After index: Index Scan on idx_appt_doctor_date
Execution time: 0.42 ms (~43× faster)
Planning time: 0.08 ms

Key point: Indexes are the single biggest performance lever after normalization. Without idx_appt_doctor_date, every doctor schedule query does a sequential scan of the entire appointment table. The EXPLAIN ANALYZE output shows a real 43x improvement for this query pattern.
